# ADR 0009 — Postgres via Zalando postgres-operator (single shared cluster)

Date: 2026-05-19
Status: Accepted
Supersedes: the CNPG decision implicit in ADR 0002 / 0004

## Context

The umbrella previously emitted one `postgresql.cnpg.io/v1 Cluster` CR **per
sub-chart** (LanCore + four satellites) when `database.createCluster: true`,
or expected an external connection per sub-chart otherwise. This produced
five separate Postgres clusters on a single deployment, which is wasteful for
the typical Lan-Software target (one LAN party / homelab / small k3s node)
and made cross-cutting concerns (backups, monitoring, version bumps) five
times harder than necessary.

Independently, the maintainer needs a values-level toggle between "let the
chart provision Postgres" and "I already have a database" — the previous
shape required setting `createCluster: false` AND populating
`database.existing.*` per sub-chart by hand, which is error-prone.

## Decision

1. **Replace CloudNativePG with the Zalando postgres-operator.**
   The chart emits exactly one `acid.zalan.do/v1 postgresql` CR from the
   umbrella (`charts/lan-software/templates/postgres-cluster.yaml`). The
   five per-app `cnpg-cluster.yaml` templates are deleted.

2. **One shared cluster, per-app database + role.**
   The single `postgresql` CR declares `spec.databases` and `spec.users`
   listing each Lan-Software app. The operator creates a database (`lancore`,
   `lanbrackets`, …) plus a login role of the same name, and provisions a
   K8s Secret per role following the Zalando naming convention:
   ```
   <role>.<clusterName>.credentials.postgresql.acid.zalan.do
   ```
   Each sub-chart's `database.existing.passwordSecret.name` defaults to
   empty; the `lan-common.dbPasswordSecretName` helper resolves to the
   Zalando secret name at template time.

3. **Single values-level toggle: `global.database.provider`.**
   - `zalando` (default) — operator-managed, shared cluster as above.
   - `external` — no CR rendered; apps connect to
     `global.database.external.host` (or per-app `database.existing.host`)
     and use the operator-supplied `passwordSecret`.

## Consequences

- One Postgres install per release instead of five — substantially less
  CPU/memory/storage on small clusters (k3s test rollout fits a single node).
- Cross-app analytics and joins are physically possible (same engine, same
  HBA) without cross-database FDWs. They are still discouraged for
  inter-service coupling reasons.
- Per-app role/db isolation is preserved at the SQL layer (each owner role
  can only access its own database).
- ADR-0002 still holds: the postgres-operator install itself remains a
  cluster-scoped prerequisite (see `docs/operators.md`).
- Existing CNPG-based deployments must migrate. The supported path is to
  `pg_dump` per database, install the postgres-operator, helm upgrade, then
  `pg_restore` into the new shared cluster. There is no in-place CR
  conversion.

## Alternatives considered

- **Keep CloudNativePG, swap to a single shared CNPG cluster.** Would solve
  the multi-cluster waste but not the maintainer's interest in trying the
  Zalando operator on a k3s test cluster. CNPG remains a fine option and may
  return as a third `provider:` value in the future if there is demand.
- **Three-way `provider: cnpg | zalando | external`.** Rejected for now —
  doubles the test surface of `_db.tpl` and the postgres-cluster template
  without immediate need. Re-introduce when at least one deployment actually
  needs both side by side.

## Implementation notes

- The Zalando postgresql CR `metadata.name` must start with the team
  prefix; defaults are `teamId: lan`, `clusterName: lan-postgres`.
- Role names must be lowercase with no underscores (Zalando normalises the
  secret name and rejects mixed case / underscored roles in some versions).
  Default role names match the app slugs: `lancore`, `lanbrackets`, etc.
- The credentials Secret is generated by the operator, not the chart — the
  chart only references its name. This means the Secret may not exist on
  the very first install before the operator reconciles; the pre-upgrade
  migration Job already retries on missing Secret references.
